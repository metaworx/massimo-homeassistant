# NOTE OnBehalf v1.0: how the run went

The `PLAN++` run of 2026-11-15, Blocks 1 to 4, and where it went
differently from v1.0.

## Where the work differs from the plan

1. **The role `integration` is a registration's alone.**
   Massimo's `main` no longer lets anyone give it by hand
   (its 5ff8571, "One identities table for providers and integrations"):
   `POST /api/v1/users` with it answers 403.
   The tests' fixture therefore registers its integration, approving the
   request with the owner token, and the key typed by hand in the tests is
   an operator's.
   The texts no longer ask for a user of the role `integration`:
   a typed key is any user's who may read.
   A key made before, such as the owner's on the live server, keeps working
   without the header and gets the repair `register`.
2. **The flow's steps**: `user` and `reconfigure` take the address,
   `sign_in` is the menu, `api_key` the key form;
   `zeroconf_confirm` and `reauth_confirm` show no form of their own any
   more, they lead to `sign_in` or `api_key`.
   Home Assistant cancels a progress task itself when a flow is left, so the
   flow has no cancel of its own.
3. **The record's `url` is checked first**: it is taken only where the same
   node answers there, since without an address set by the owner Massimo
   announces `<node>.local`, which not every Home Assistant resolves.
4. **The repair `instance_pending`** is raised when the entry is set up,
   from `/me`'s `instance_id`, and one call with the header then makes
   Massimo note this installation's id for the owner to accept; it goes at
   the next call let through. A refusal with that code raises it too.
5. **An automation's level** is `admin`, the system's in Home Assistant;
   Massimo adds nothing to it beyond the integration's own role.
6. **Massimo's audit** names a call without a user as
   `homeassistant.system`, with `via` and `for` in its `detail`;
   `test_the_key_lock_writes_through_massimo` reads it there.
